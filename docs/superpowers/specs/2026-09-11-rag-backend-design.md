# RAG 学习引擎后端架构设计方案

日期：2026-09-11。状态：已定稿，用户已确认全部约定无疑问。本文件只设计后端，不实现业务代码。

## 1. 已确认的需求

- 使用 FastAPI；业务接口全部使用 POST。
- API 层定义接口，Service 层实现业务逻辑，Schemas 规范输入输出。
- 实现全局异常处理、统一响应格式、统一路由注册。
- 第一版展示文档解析、分块、召回和重排，不生成答案。
- 支持多个文档，共用一个默认知识库；重启后保留文档与索引。
- 上传接口通过 multipart/form-data 接收文件并保存到本地；按文件名（含扩展名）和字节大小联合判重。
- 使用已保存本地文件的 URL 定位文档并发起解析。
- 文件查看接口同样使用 POST，不提供原文件 GET 访问。
- 每份文档只保留一套生效向量索引，不提供多套索引选择或历史版本对比。
- 索引后台构建，无 MQ；重建成功后替换，失败只清理本次构建产生的数据，保留旧生效索引和原文件。首次构建失败回到未入库状态。
- 支持 CORS，按用户“访问范围开全部”设置允许所有来源；不使用跨域 Cookie 凭证。
- 分块预览只读，不提供用户编辑分块功能。
- 项目用于学习，优先复用现有组件。

## 2. 当前代码与设计影响

| 现状 | 对后端设计的影响 |
| --- | --- |

| 全局切分器缓存并修改策略实例 | 请求应使用独立策略实例；模型等昂贵资源仍复用 |
| 模型和部分存储资源在导入时初始化 | 将资源初始化与关闭纳入 FastAPI 生命周期，便于启动检查和隔离测试 |
| `get_chroma()` 实际读取 `redis_handler` | 依赖注入需要与实际应用状态字段对应 |

| 已存在未提交的启动文件和回归测试 | 实现时保留用户改动；本次设计不覆盖它们 |

此外，当前父子检索只要命中父块就走父块返回分支。多文档使用不同切分策略时，需要保留普通块与父块混合结果，避免普通块被丢弃。

## 3. 整体结构

采用单体分层应用。现有规模不需要微服务、通用 Repository 框架或插件平台。

```text
前端
  → FastAPI /api/v1
  → API：路由、请求声明、响应声明、依赖注入
  → Service：文档管理、预览、索引生命周期、检索业务
  → RAG 引擎：解析、分块、嵌入、检索、重排
  → 本地文件 + PostgreSQL + 持久化 Chroma
```

| 位置 | 职责 |
| --- | --- |
| `run.py` | 本地启动入口 |
| `app/__init__.py` | 创建 FastAPI 应用，注册生命周期、路由和异常处理 |
| `app/api/` | 按文档、索引、检索、系统信息组织接口；集中注册路由 |
| `app/service/` | 对应业务流程；复用现有引擎与 ORM，处理资源状态和事务边界 |
| `app/Schemas/` | 请求、响应、分页模型；保留项目已有 `Schemas` 大小写风格 |
| `app/model/` | 文档等业务实体及已有父块实体 |
| `app/dependencies/` | 获取应用级引擎资源和请求级数据库会话 |
| `app/libs/` | 业务错误定义、错误码等少量共享内容 |
| `tool/rag_engine/` | 框架无关的 RAG 能力及内部结果类型 |

Service 返回业务结果，API 声明统一响应模型。引擎不依赖 HTTP 请求、HTTP 状态码或 API 响应包装。API 中只保留声明、依赖注入、调用 Service 和响应转换，不直接编排 ORM 或算法。

在 `app/api/__init__.py` 定义总 APIRouter，集中 include 各模块路由及 tags；应用只 include 一次总路由并设置 `/api/v1` 前缀。不使用动态扫描注册。统一响应模型放 `app/Schemas/response.py`，异常定义及处理器集中在 `app/libs/exceptions.py`，后台执行器放 `app/service/index_service.py`，避免额外平台层。

## 4. 统一接口约定

业务路由统一前缀 `/api/v1`，按资源与动作命名。文件上传使用 POST multipart，其余主要使用 POST JSON。multipart 字段与响应同样需要明确校验和文档声明。

成功响应示例：

```json
{"code": "OK", "message": "成功", "data": {"items": []}, "request_id": "..."}
```

失败响应示例：

```json
{"code": "DOCUMENT_NOT_FOUND", "message": "文档不存在", "data": null, "request_id": "..."}
```

- 使用 Pydantic 泛型响应模型表达 `data` 类型；不要使用中间件读取并重新包装所有响应体。
- 保留 HTTP 语义：成功 200；接受后台任务用 202；参数问题 422；不存在 404；状态冲突 409；未知错误 500；上游服务异常按情况使用 502、503、504。
- 全局注册请求校验异常、业务异常、Starlette HTTP 异常及未知异常处理器。响应校验失败属于服务端错误，不作为用户参数错误。
- 保留 HTTP 异常必要的响应头。客户端不接收堆栈、凭证、数据库连接串或供应商原始错误对象。
- 统一生成 `request_id`，同时写入响应与日志。记录接口、耗时及失败阶段，默认不记录完整文档正文。
- 不将所有 `ValueError` 直接认定为客户端错误；只有明确的输入校验错误才能转为业务错误。
- 页列表使用 `items、total、page、page_size`；所有雪花 ID 在 JSON 中使用字符串，避免浏览器整数精度丢失。
- 文件查看在内的所有业务接口均使用 POST；OpenAPI、Swagger UI 使用框架 GET，浏览器 CORS 预检使用 OPTIONS，不为原始文件挂载 StaticFiles。
- 文件查看成功返回二进制文件流，不套 JSON 外壳；发送文件前发生的失败仍使用统一 JSON 错误响应。该响应边界已确认。流发送开始后的磁盘或网络错误只能记录日志并中断传输，不能再改写为 JSON 错误。

### 异常契约

JSON 成功与失败保留相同的四个顶层字段。失败时 `data` 通常为 null；参数错误允许返回受限的字段错误对象，例如：

```json
{"code": "VALIDATION_ERROR", "message": "请求参数不合法", "data": {"errors": [{"field": "body.chunk_size", "message": "必须大于 0", "type": "greater_than"}]}, "request_id": "..."}
```

只提取错误字段、类型和安全提示，不直接序列化校验异常中的原始 input 或 ctx。业务成功模型和公共错误模型均在 OpenAPI 中声明。

| 场景 | HTTP 状态 | 错误码 |
| --- | --- | --- |
| 文件名（含扩展名）及字节大小均重复 | 409 | DOCUMENT_ALREADY_EXISTS |
| 文件或文档记录不存在 | 404 | DOCUMENT_NOT_FOUND |
| 上传超出大小上限 | 413 | FILE_TOO_LARGE |
| 文件类型不支持 | 415 | UNSUPPORTED_FILE_TYPE |
| 参数校验失败 | 422 | VALIDATION_ERROR |
| 文档解析为空或已确认文件内容无法解析 | 422 | DOCUMENT_UNPARSABLE |
| 文档当前状态不允许该操作 | 409 | DOCUMENT_STATE_CONFLICT |
| 上游模型服务响应异常 | 502 | MODEL_UPSTREAM_ERROR |
| 必要依赖不可用 | 503 | DEPENDENCY_UNAVAILABLE |
| 上游模型调用超时 | 504 | MODEL_TIMEOUT |
| 意外内部错误 | 500 | INTERNAL_ERROR |

未知解析器错误仍按内部错误处理，不能全部归咎于用户文件。Service 仅捕获需要转换语义、更新状态或补偿资源的异常，其余交给全局处理器。底层日志不输出供应商响应中的凭证。

已选择后台任务模式。请求返回后发生的失败由任务执行器捕获并保存安全错误码、失败阶段和关联 request_id，状态查询接口负责展示。全局异常处理器不能修改已经发出的 HTTP 响应，也不能替代后台任务失败处理。真实超时与线程取消能力需要区分：`asyncio.to_thread` 的等待被取消，不代表底层 SDK 已停止运行。

## 5. 第一版功能与接口

| 功能 | 接口 | 说明 |
| --- | --- | --- |
| 上传文档 | `/documents/upload` | 保存受限大小的文件，分配 document_id；不接受任意服务器路径 |
| 查看原文件 | `/documents/view/{document_id}` | POST 获取原始文件流；此地址就是上传结果中的 file_url |
| 文档列表和详情 | `/documents/list`、`/documents/detail` | 显示名称、大小、时间、解析及索引状态 |
| 删除文档 | `/documents/delete` | 协调清理文件、父块、向量及文档记录；失败不能伪报成功 |
| 解析预览 | `/documents/parse` | 返回解析后的 Markdown，可复用解析产物 |
| 分块预览 | `/documents/chunks/preview` | 指定策略参数，展示内容、数量、长度与父子关系；预览不写入生效向量索引 |
| 构建索引 | `/indexes/build` | 提交后台构建任务，返回 HTTP 202 和 task_id |
| 查询任务 | `/tasks/detail` | POST 传入 task_id，返回状态、当前阶段、计数及安全错误信息 |
| 查看索引 | `/indexes/detail`、`/indexes/chunks/list` | 查看状态、实际分块参数及已经入库的分块 |
| 检索调试 | `/retrieval/search` | 返回初检、重排及最终上下文，并支持按文档过滤 |
| 能力与状态 | `/system/capabilities`、`/system/health` | 查询可用策略、参数约束、模型身份及基础依赖状态；不暴露密钥 |

上述地址均在 `/api/v1` 下，统一 POST。文件查看路径参数同样需要类型校验；上传返回 document_id、file_url、original_filename、size_bytes。其余单文档操作传入 file_url；构建额外传入策略配置，任务查询传入 task_id。

文件 URL 示例：`http://localhost:8000/api/v1/documents/view/123456789`。前端对该 URL 发起 POST，先检查 HTTP 状态和内容类型，再读取 Blob。PDF 可通过 Blob URL 预览，其他格式按浏览器能力下载；HTML、XML 等主动内容强制作为附件，不渲染为可信页面。返回安全 Content-Type、Content-Disposition、X-Content-Type-Options: nosniff、X-Request-ID，CORS 暴露 Content-Disposition 以便前端读取文件名。JSON、文本等原文件也直接传原始字节，不因扩展名改成响应封装。

Service 验证记录为 ready 并取得文件读取句柄，API 将其转换为文件流；文件读取期间禁止删除同一文件，采用请求级占用计数，流结束或断开时在 finally 中释放。删除遇到占用返回 409，防止 Windows 打开文件删除失败和流中途丢失。解析和预览读取文件使用同一占用约定。

解析与只读预览第一版采用请求内执行，阻塞解析/切分移入线程；只有索引构建进入后台队列。预览分页默认每页 20、最大 100，返回 total 和 strategy_config；父子模式分页子块，并返回这一页关联的父块。原文不接受客户端修改后回传。分块参数采用 Pydantic 带 discriminator 的策略模型，按 fixed_length、semantic、recursive、structural、parent_child 校验，未知字段拒绝；parent_child 的父策略、子策略只允许非父子策略，禁止无限嵌套。chunk_size 用字符数表达，overlap 必须满足 0 ≤ overlap < chunk_size，语义策略不接受 overlap。预览和构建共享同一配置模型。

检索结果应区分候选召回数量 `candidate_k` 与最终上下文数量 `top_k`，并保留原始召回排名、重排排名、距离、重排分数和去重后的父块上下文。距离通常越小越相似，重排分数通常越大越相关；二者不是同一种分值，也不是准确率。记录实际距离度量和模型身份，不承诺不同模型的分数可以直接比较。

空检索结果返回成功及空列表；父块缺失等索引完整性问题必须可诊断，不能静默表现为没有命中。第一版不默认返回高维向量。

### 检索展示契约

请求字段为 `query`、可选的 `file_urls`、`candidate_k`、`top_k`、`rerank`。query 去掉首尾空白后需非空，最大 2000 字符；candidate_k 默认 20、范围 1–100；top_k 默认 5、范围 1–20，且不得超过 candidate_k。不向前端透传任意 Chroma where 表达式，由 Service 从已登记的文件 URL 和生效构建 ID 生成过滤条件。

省略 file_urls 表示在默认知识库所有已生效文档中检索；显式空列表视为参数错误，避免误查全库。显式指定的 URL 不存在返回 404，指定未入库文档返回 409。全库没有生效文档时返回成功空列表及 `NO_ACTIVE_INDEX` 提示。

| 响应 data 字段 | 含义 |
| --- | --- |
| `candidates` | 按初检顺序列出 chunk_id、document_id、file_url、文件名、文本、parent_id、标题路径、distance、retrieval_rank |
| `reranked` | 开启重排时返回 chunk_id、rerank_score、rerank_rank 和 retrieval_rank；关闭时为 null，开启但无命中时为空列表 |
| `contexts` | 最终上下文：文本、来源、context_id、rank、matched_chunk_ids，以及决定该上下文顺序的代表命中 ID |
| `timings_ms` | query_embedding、vector_search、parent_lookup、rerank、total 的实际耗时；未执行阶段为 null |
| `effective_config` | 实际候选数限制、最终数限制、嵌入模型、距离度量、重排模型及是否执行重排 |
| `warnings` | 空索引或去重后结果不足等可解释提示；正常时为空列表 |

流程：先以生效索引为范围召回 candidate_k 条；获取候选对应的父块文本快照；若开启重排则对全部候选评分排序；随后按顺序合并属于同一父块的命中，普通块独立保留，最后截取 top_k 个上下文。父块以最高排名子块的位置排序，并附上该候选集合中命中的子块 ID，不伪造一个父块相似度分数。去重后不足 top_k 时不额外补查，返回实际数量。

重排模型返回原始候选索引与分数，再据索引定位 chunk_id；不能用正文字符串反查身份。同文不同块的距离、来源和分数必须分别保留。重排失败按上游异常返回，不静默退回初检结果造成页面误认为重排成功。

第一版展示解析 Markdown、分块内容及父子关系，不承诺原 PDF 坐标高亮。预览块 ID 仅用于当前预览的父子关联，不保证与后续构建的块 ID 相同；预览和入库使用同一策略配置规则，已入库块由索引分块列表查询。

## 6. 数据与资源原则

- 本地目录保存原始文件及必要解析产物，PostgreSQL 保存文档、索引状态及父块，Chroma 保存检索块和向量。
- 文件名用于展示和同名判重；服务器控制实际存储路径。校验文件类型、上传大小及空文本；不将解析出的 HTML 当成可信内容。
- 判重通过 PostgreSQL 的 `(filename_key, size_bytes)` 联合唯一约束兜底，避免并发上传绕过检查；重复上传返回 HTTP 409 和 `DOCUMENT_ALREADY_EXISTS`。文件大小在流式保存时累计即可，无需引入依赖或内容哈希。
- filename_key 使用含扩展名的完整文件名，按 Unicode NFC 规范化并忽略大小写。同名且大小不同允许分别上传，各自分配独立目录和 URL，绝不覆盖已有文件。同名且大小相同但内容不同仍判重复，这是用户指定规则的限制，不进行内容去重。
- 文件 URL 定位原始文档，不等同于检索使用的向量索引。前端可使用 URL 指定文档，内部 document_id 用于关联数据库记录及分块，不要求前端管理多份文档标识。
- 上传成功后返回 POST 文件查看地址 `file_url`；后续接口据此查找已登记的 document_id，再复用现有解析器读取本地文件，不向自身发起 HTTP 下载。URL 与存储路径由服务端关联，不直接将用户提交的 URL 拼接成磁盘路径，也不支持外部 URL。浏览器地址栏默认发送 GET，不能直接粘贴此 URL 查看文件，前端使用 POST 获取 Blob。
- CORS 使用 FastAPI/Starlette 的 CORSMiddleware：`allow_origins=["*"]`、`allow_credentials=False`、`allow_methods=["*"]`、`allow_headers=["*"]`，暴露 X-Request-ID、Retry-After 和 Content-Disposition 响应头。放开 CORS 方法不等于注册额外业务方法，业务路由仍只声明 POST。预检 OPTIONS 由框架处理，错误响应也应包含适用的 CORS 响应头；通过最外层 CORS 包装保证未处理异常生成的 500 响应也满足这一点。
- 第一版按学习项目开放调用，不增加登录、用户权限或 API Key 模块。监听地址默认 `0.0.0.0`、端口 8000，可通过配置修改；监听所有网卡与 CORS 允许所有来源是两个独立设置。对外生成的文件 URL 使用配置的公开基础地址，不使用 `0.0.0.0` 作为 URL 主机名。
- 文档与向量通过 `document_id` 关联，索引记录实际切分配置、嵌入模型、向量维度和距离度量。
- 同一个检索集合必须使用兼容的嵌入空间；不能因为向量维度相同就混用模型。模型变更需要明确的重建策略。
- PostgreSQL 事务不能回滚 Chroma 或本地文件操作；需要可见的失败状态、可重复执行的清理和重试规则。
- 已确认只有一套生效索引，重建成功后替换。构建与清理期间允许临时保留新旧数据，但它们不能同时生效，不提供历史版本入口；查询不得混入未生效分块。失败仅清理本次构建的分块、父块和向量，保留旧生效索引和原文件。
- 同步 SDK、文件解析和语义分块等阻塞工作不能直接占用异步事件循环。共享模型需限制并发；策略实例不跨请求共享可变状态。
- 生命周期负责资源初始化、失败时清理及关闭。服务已启动不等于全部依赖可用，健康检查需表达实际状态。

### 最小数据模型

保留现有 `rag_engine` 数据库 schema，新增两张业务表并扩充父块表，不另建知识库表或通用任务平台。

| 实体 | 主要字段与约束 |
| --- | --- |
| Document | document_id、original_filename、filename_key、size_bytes、storage_key、upload_status、active_build_id（可空）、created_at；filename_key 与 size_bytes 联合唯一，storage_key 唯一 |
| IndexBuild | build_id、document_id、status、stage、strategy_config、embedding_config、chunk_count、parent_count、completed_chunks、total_chunks、request_id、error_code、error_message、cleanup_pending、时间字段 |
| ParentChunk | 保留 chunk_id、document、metadata、create_time；增加 document_id、build_id 及查询/清理用索引 |
| Chroma 记录 | id 为 chunk_id 字符串；document 为分块正文；embedding 为向量；metadata 包含 document_id、build_id、chunk_index、可选 parent_id、标题路径 |

`task_id` 对外直接使用 build_id，不额外维护两套 ID。IndexBuild 同时承载构建状态及生效配置快照；active_build_id 指向本文件成功发布的构建记录。历史失败记录仅用于诊断和清理，不提供多版本检索功能。

file_url 根据公开基础地址和固定文件查看路径中的 document_id 生成，数据库保存 storage_key 及文件归属。只接受配置基础地址下、路径符合该模板且对应已登记记录的 URL，不允许查询参数、片段或跨目录路径；不能从请求 Host 直接生成可信基础地址。主机地址变更后以新返回的 URL 为准，内部关联仍以 document_id 保持稳定。

Document 的 upload_status 表达 uploading、ready、deleting、delete_failed；索引可用性由 active_build_id 表达，构建进度由 IndexBuild 表达，避免同一个 status 同时表示上传成功、构建失败和旧索引仍有效。同一文档 queued/running 构建通过 PostgreSQL 部分唯一索引限制为一个。

清理旧版本时先持久化其 cleanup_pending，再切换指针，两者放在同一发布事务；恢复时只删除已明确标记待清理且不再被 active_build_id 引用的构建。清理完成后才能清除标记。删除文档前先置 deleting 并使其退出检索范围，再清理全部关联构建、向量、父块和文件，最后删除记录释放判重键；失败保留删除状态供重试。第一版删除期间与该文档的构建互斥。

原始文件保存至配置目录下的独立文档目录；解析 Markdown 可作为同目录缓存保存，服务端原子替换，分块预览不持久化向量。数据库 schema 创建、表结构升级和 Chroma 持久化目录必须写入启动说明，不以生产启动时隐式删表或覆盖已有索引完成初始化。

## 7. 执行与上传边界

### 上传默认边界

用户已授权采用常规默认值，第一版约定如下，保留配置项便于后续调整：

- 每次上传一个文件；文件有效载荷 1 字节至 20 MiB（20 × 1024 × 1024 字节）。总 multipart 请求体限制 21 MiB，用于容纳表单开销，超限统一返回 413。
- 以流式计数限制实际收到的请求体，不能仅信任 Content-Length；文件内容再单独计数。实现时应验证所安装 Starlette 版本的 multipart 限制，不能依赖接口函数拿到 UploadFile 后才控制整个请求体大小。
- 文件名最多 255 个字符，拒绝空名、路径分隔符、控制字符和路径穿越；实际存储使用服务器生成的独立目录及安全文件名，避免 Windows 保留名和尾部点号规则影响保存。
- 扩展名沿用解析器白名单：md、markdown、txt、html、htm、csv、json、xml、docx、pdf、xlsx。扩展名允许不代表文件可成功解析；扫描 PDF 无 OCR 文本时给出可诊断错误，第一版不新增 OCR。
- 临时文件接收完整后，用实际大小执行联合判重并登记上传状态，成功保存后才发布可用 URL；冲突或失败清理临时文件。原文件保存成功后才允许解析、预览和入库。
- 完整删除文档并成功清理其关联数据后释放判重记录，允许再次上传；删除失败保留记录和可重试状态。

### 无 MQ 后台任务方案

使用 lifespan 启动一个后台 worker 协程和 `asyncio.Queue`；只运行一个 Uvicorn worker、一个应用实例。队列只保存 task_id，PostgreSQL 保存任务状态及参数，worker 从数据库读取实际任务。无需另建调度框架。

1. `/indexes/build` 校验 file_url 与策略参数，在数据库事务中创建任务及唯一 build_id；同一文档不能同时排队构建、重建或删除，冲突返回 409。
2. 提交事务后入内存队列，再返回 202。队列初始上限 20 个等待任务；短临界区串行执行容量检查和提交，避免并发超额。满队列拒绝接收并返回 503 `TASK_QUEUE_FULL`，附 Retry-After。如果提交后未能入队，任务须转失败，不能虚报已接受。
3. worker 使用独立数据库会话，按顺序执行解析、切分、嵌入、写入、发布、清理；不持有请求会话或横跨模型调用的长事务。只有一个构建任务执行，检索和状态查询仍可处理。
4. 状态为 `queued → running → succeeded / failed`；另存 `stage`、`completed_chunks`、`total_chunks`、起止时间、错误码及清理状态。对尚不知总量的阶段只展示阶段，不伪造整体百分比。
5. 前端每 1 秒用 POST 查询任务，进入终态后停止；首次构建失败表示文档无可用索引，重建失败保留旧生效索引。状态响应区分本次任务结果和文档是否仍有可用索引。
6. 每个任务异常在 worker 内捕获并记录，避免一个失败任务退出整个消费循环；若 worker 意外退出，健康检查标为不可接收任务，而非继续返回接受成功。
7. 重启时先恢复清理，再接收任务：未发布的 queued/running 任务标记 `PROCESS_INTERRUPTED`，尝试删除该 build_id 的向量和父块，用户手动重试。已提交发布事务的索引视为有效，不能因后续清理被打断而误删。
8. 清理失败记录 `cleanup_pending`，保留定位残留数据的 build_id，启动时和显式重试时再次清理；残留数据不得参与检索。失败任务的诊断记录保留，删除的是构建数据，不是错误证据。
9. 关闭时停止接单并等待当前任务至优雅关闭期限；超时后留给下次启动恢复。线程内 SDK 必须设置其支持的超时；未确认写入已停止前，不与仍运行的写入线程并发执行最终清理。

为每次构建的向量和父块记录 build_id，文档记录 active_build_id。查询应在 Chroma 召回之前限定生效 build_id，不能先 top-k 再剔除残留数据，否则可能漏掉真正命中。发布时在 PostgreSQL 短事务中切换 active_build_id 并标记任务成功，之后清理旧数据；旧数据清理失败单独报告，不撤销已经生效的新索引。

发布与查询取得生效列表、向量命中及父块原文的过程使用同一进程内短读写临界区（第一版可用一个 asyncio.Lock），避免查询仍引用旧父块时被删除；嵌入、重排及长时间构建在锁外完成。此设计只面向学习项目的小规模单实例，扩展多进程时需要独立任务消费者与跨进程协调，不能仅提高 Uvicorn workers 数量。

## 8. 实施顺序与验收

按四个阶段实施，每个阶段都有可调用接口及可验证结果：

1. 应用基础：启动入口、lifespan、Schemas、统一路由、统一异常和响应、CORS、依赖配置与数据库建表脚本。
2. 文档流程：表单上传和联合判重、POST 文件查看、文档管理、解析及只读分块预览。
3. 持久化索引：Chroma 落盘、构建记录、后台队列、状态查询、新索引发布、失败与重启恢复、删除清理。
4. 检索可视化：结构化命中、稳定的重排身份、父子与普通块混合结果、参数与耗时输出；最后做真实集成验收。

- API 契约：业务路由方法和前缀正确；成功、校验失败、不存在及未知异常均符合统一响应，HTTP 状态正确。
- 预览与检索：策略参数生效；父子关系正确；重复正文不造成命中 ID 或排名错配；混合普通块与父子块不丢结果。
- 持久化：重启后文档、索引及父块关系仍有效；删除后不再检索到对应内容。
- 失败恢复：模拟嵌入或存储失败，检查状态、重试和残留数据处理，验证旧索引可用性；覆盖“数据库已提交但未入队”和“已发布但未清理”两处中断窗口。
- 文件契约：同名同大小拒绝，同名不同大小独立保存；20 MiB 边界、路径穿越、POST 文件流及失败 JSON 正确；GET 文件查看返回统一 405；文件读取期间删除返回冲突。
- CORS：任意 Origin 的合法预检及成功、422、404、500 响应均符合约定；禁用凭证跨域；无需启动真实模型即可验证路由和错误格式。
- 并发隔离：不同文档使用不同切分参数时互不污染。
- 使用标准库 unittest 隔离模型、API 和数据库；语法检查、行为测试与真实集成验证分别报告。
- 实现阶段补齐 Python 3.12.10 环境、依赖清单、脱敏配置样例、数据库初始化方式和启动说明。

## 9. 后续学习方向与本期范围

第一版不包含答案生成、对话历史、自动评测平台、混合检索、Agent、多知识库和多租户，也不引入 Redis、Celery 或消息中间件。后续优先增加一组人工标注查询与目标文档，用 Recall@k、MRR 和耗时评估检索；有对比数据后再考虑 BM25 混合检索、查询改写或自动评测。答案生成放在上层 Service，保持引擎输出检索上下文的职责。

模型选择第一版通过配置固定，不提供页面任意切换嵌入模型。持久化集合记录模型身份、维度和距离度量，启动时检查匹配；不匹配则拒绝索引读写，提示恢复原配置或显式重建全库，不自动清空数据。这样避免同维度不同模型被误混用。

## 10. 整体评审确认项

用户已确认以下实现约定和默认值无疑问，可以定稿：

1. 文件查看成功返回二进制流，是统一 JSON 的唯一业务成功例外；失败发送前仍返回统一 JSON。全部业务 POST，框架文档 GET 与 CORS OPTIONS 保留。
2. 无 MQ 采用单实例、单消费者队列和 PostgreSQL 状态；重启不自动续跑中断任务，清理后由用户手动重试。
3. 文件名含扩展名，NFC 规范化并忽略大小写后与字节大小联合判重；同名不同大小允许独立保存；完整删除后允许再次上传。
4. 上传每次一个、最大 20 MiB；CORS 全开放、无登录模块；监听地址默认 0.0.0.0:8000，公开 URL 基础地址单独配置。
5. 统一 JSON 使用 code、message、data、request_id，并保留正确 HTTP 状态；第一版接口和检索展示字段按本文执行。

本方案已完成需求核对与一致性检查，无未决设计问题。本轮交付为架构方案；业务代码实现及集成验证属于后续实施任务。
